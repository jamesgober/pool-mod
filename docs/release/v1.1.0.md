# pool-mod v1.1.0

Fixes from an independent review of 1.0.0. There is no breaking API change and
the MSRV stays at Rust 1.75. A few runtime behaviors change; they are listed
below so you can check them against your use.

## Fixed

### A panicking hook no longer leaks a slot

In 1.0.0 the pool counted a slot as taken before calling `create`, `validate` or
`recycle`, and gave it back only when the hook returned. If the hook panicked
(a driver that panics on a malformed reply, inside a server that catches panics
per request), the slot stayed taken with no resource behind it. After `max_size`
such panics, every `get` returned `Error::Timeout` for the life of the pool.

Each hook now runs under a guard that gives the slot back on unwind, and the
resource is dropped. The panic still reaches the caller. A guard dropped while
its own thread is panicking is now discarded without calling `recycle`: the
resource may have been left half way through an operation, and a second panic
during unwinding would abort the process.

### `Duration::MAX` timeouts no longer panic

`get_timeout(Duration::MAX)`, and `get` with `create_timeout` set to
`Duration::MAX`, panicked on `Instant` overflow. A timeout too large to
represent now waits indefinitely.

## Added

- `Pool::try_get_idle()` hands out an idle resource or returns `Error::Timeout`
  at once. It never calls `create`.
- `Manager::create_with_deadline(&self, deadline: Option<Instant>)` is a provided
  method whose default calls `create()`. The pool always creates through it and
  passes the caller's deadline, so a manager can set its connect timeout from the
  time the caller has left. Existing managers are unaffected.
- `Pooled::discard(guard)` drops a resource that is known to be broken instead of
  returning it to the pool, and `Pooled::detach(guard)` takes the resource out of
  the pool for good. Both free the slot. They are associated functions, so they
  never shadow a method of your resource.

## Changed

- **Timeouts bound waiting, not `create`.** This was already how 1.0.0 behaved;
  the docs now say so. `get_timeout(50ms)` can still take as long as a `create`
  takes once it has started, and `try_get` never waits for another thread but
  may run `create`. Use `create_with_deadline` or `try_get_idle` to bound it.
- **`min_idle` is refilled by the reaper.** With `reap_interval` set, each pass
  creates resources until the idle set is back at `min_idle`, never past
  `max_size`. Without a reaper, `min_idle` resources are created at build time
  and the idle set is refilled only on demand, as before.
- **Idle resources are reused last in, first out.** Under light load the same few
  resources are reused and the rest reach `idle_timeout` and expire. In 1.0.0
  checkout rotated through every idle resource and kept all of them open.
- **Waiting is bounded.** Waiting threads are served in arrival order, and a
  returned resource is offered to the one that has waited longest. A newly
  arriving thread may still take a free resource first, but only while the
  oldest waiter has waited less than about a millisecond; after that, newcomers
  queue behind the waiters. In 1.0.0 a newcomer could take a returned resource
  ahead of a waiter for as long as the pool stayed saturated, so an early waiter
  could time out while later arrivals succeeded.
- Checkout no longer reads the clock when no expiry policy is set.

## Performance

Measured on a loaded Windows x86_64 machine, Rust 1.99, against 1.0.0 built
the same way, two rounds each.

Single-threaded Criterion benchmarks (trivial resource):

| Benchmark              | 1.0.0          | 1.1.0          |
|------------------------|---------------:|---------------:|
| `get` + return (reuse) | 192 to 511 ns  | 117 to 119 ns  |
| `try_get` + return     | 337 to 741 ns  | 110 to 138 ns  |
| `status` snapshot      | 23 to 25 ns    | 13 ns          |

The 1.0.0 runs were noisy on this machine; the result to take from them is
that 1.1.0 is not slower on the uncontended path.

Contended throughput, every thread borrowing and returning in a loop for 1.5 s:

| Threads, `max_size` | 1.0.0           | 1.1.0           | Slowest thread, 1.0.0 to 1.1.0 |
|---------------------|----------------:|----------------:|-------------------------------:|
| 8, 2 (saturated)    | 2.9 to 3.0 M/s  | 3.4 to 3.6 M/s  | 206k to 277k, now 558k to 604k |
| 8, 8                | 3.4 to 3.5 M/s  | 3.7 M/s         |                                |
| 4, 4                | 4.6 to 5.0 M/s  | 5.3 to 5.4 M/s  |                                |

A strict hand-off of every returned resource to the oldest waiter was also
measured and dropped: in the saturated case it fell to 0.03 to 0.06 M/s,
because every checkout then needs a context switch.

## Upgrading

```toml
[dependencies]
pool-mod = "1.1"
```

No code changes are needed. If you relied on FIFO rotation through idle
resources, or on a guard dropped during a panic being recycled and pooled, note
the changes above.
